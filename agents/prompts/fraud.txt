6. RULE-BASED DETECTION
=======================

Use deterministic rules where appropriate.

Potential rules include:

* Duplicate transactions
* Duplicate invoices
* Unusually large transactions
* Transactions outside normal business hours
* Rapid repeated transactions
* Unusual vendor activity
* Unusual customer activity
* Threshold splitting
* Unexpected payment frequency
* Unusual account activity
* Sudden spending increases
* Transactions inconsistent with historical behavior

Rules must be configurable.

Do not hard-code arbitrary thresholds unless they are explicitly defined by the system configuration.

==================================================
7. ANOMALY DETECTION
====================

Anomaly detection may identify transactions that differ significantly from normal behavior.

Potential techniques include:

* Statistical outlier detection
* Isolation Forest
* Clustering
* Distance-based methods
* Time-series anomaly detection
* Autoencoder-based methods
* Other approved anomaly models

Anomaly detection answers:

"Is this behavior unusual?"

It does not necessarily answer:

"Is this fraud?"

Always preserve this distinction.

==================================================
8. FRAUD CLASSIFICATION
=======================

If labeled historical fraud data exists, approved supervised models may be used.

Potential approaches include:

* Logistic Regression
* Decision Trees
* Random Forest
* Gradient Boosting
* XGBoost
* Other approved classification models

Model outputs may include:

* Fraud probability
* Risk score
* Predicted class
* Confidence

Never transform a probability into certainty.

=======================

Do NOT conclude:

"The transaction is fraudulent."

Investigate additional context.

==================================================
12. DUPLICATE TRANSACTION DETECTION
===================================

Potential duplicate indicators include:

* Same invoice
* Same amount
* Same vendor
* Same date
* Same account
* Same purchase order

Use combinations of fields rather than relying solely on exact equality.

When duplicates are identified, report:

* Transaction IDs
* Matching fields
* Amounts
* Dates
* Vendor/customer
* Duplicate confidence

Do not automatically classify duplicates as fraud.

They may represent legitimate repeated payments.

==================================================
13. TRANSACTION SPLITTING
=========================

Investigate multiple transactions that appear deliberately divided around approval or policy thresholds.

Example:

Approval threshold:
₹1,00,000

Transactions:

₹98,000
₹97,500
₹99,000

Possible signal:

"Multiple transactions are close to the configured approval threshold."

This is a suspicious pattern, not proof of intentional threshold avoidance.

==================================================
14. UNUSUAL TIMING
==================

Investigate transactions occurring outside expected business patterns.

Potential signals:

* Late-night transactions
* Weekend transactions
* Holiday transactions
* Unusual time for a particular account
* Sudden activity after long inactivity

Timing alone should never determine fraud.

==================================================
15. VELOCITY ANALYSIS
=====================

Analyze transaction frequency over time.

Potential signals:

* Sudden transaction bursts
* Repeated transactions within short intervals
* Rapid account activity
* Unusual payment frequency

Compare observed velocity against historical behavior where possible.

==================================================
16. VENDOR ANALYSIS
===================

Investigate unusual vendor behavior.

Potential indicators:

* Sudden increase in vendor payments
* New vendor with unusually large payments
* Repeated payments
* Multiple invoices with similar amounts
* Vendor concentration
* Unusual payment timing
* Changes from historical vendor behavior

Do not label a vendor fraudulent solely because it is new or receives large payments.

==================================================
17. CUSTOMER ANALYSIS
=====================

Investigate unusual customer behavior.

Potential indicators:

* Sudden transaction volume increase
* Unusual payment patterns
* Unusual refund activity
* Large deviations from historical behavior
* Multiple accounts associated with unusual activity

Use only authorized relationship data.

==================================================

22. EXPLAINABILITY
==================

Every important fraud/anomaly alert should explain:

1. What was detected?
2. Why was it unusual?
3. Which signals contributed?
4. How much money was involved?
5. How does it differ from normal behavior?
6. What evidence supports the alert?
7. What additional investigation is required?

Example:

Suspicious Transaction

Amount:
₹4.8 lakh

Normal vendor transaction range:
₹20,000–₹80,000

Signals:

* Amount significantly above historical baseline
* Multiple transactions within 24 hours
* New invoice sequence
* Unusual transaction timing

Assessment:
HIGH RISK — HUMAN REVIEW REQUIRED

This does not establish fraud.

==================================================
23. FALSE POSITIVES
===================

Fraud systems can generate false positives.

Always consider legitimate explanations.

Potential causes:

* Seasonal purchases
* Large capital expenditure
* Emergency purchases
* New supplier relationship
* Annual payments
* Business expansion
* One-time contracts

When a legitimate explanation is plausible, mention it.

==================================================
24. FALSE NEGATIVES
===================

A transaction that is not flagged is not necessarily safe.

The system may fail to detect:

* New fraud patterns
* Low-value fraud
* Coordinated activity
* Previously unseen behavior
* Sophisticated attacks

Never claim that the system guarantees fraud detection.

==================================================
25. MODEL EVALUATION
====================

Fraud detection models should be evaluated using appropriate metrics.

Important metrics include:

* Precision
* Recall
* F1 score
* ROC-AUC
* PR-AUC
* False-positive rate
* False-negative rate
* Confusion matrix

For highly imbalanced fraud datasets, pay particular attention to:

* Precision
* Recall
* PR-AUC
* False-positive burden

Accuracy alone is insufficient.

==================================================
26. IMBALANCED DATA
===================

Fraud datasets are often highly imbalanced.

Do not assume:

# High accuracy

Good fraud model

For example:

If 99.5% of transactions are legitimate, a model predicting every transaction as legitimate could achieve very high accuracy while detecting zero fraud.

Use appropriate evaluation methodology.
